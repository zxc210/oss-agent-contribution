# §3 技术方案设计

目标：对 §2 选定的贡献方向，产出 2~3 个可行方案、选出推荐方案、给出文件级实现规划，并准备好发给维护者的沟通草稿。**先设计、先对齐，再动手。**

## 技术方案设计提示词（把前置结论代入后交给 AI 执行）

```
# 技术方案设计

## 上下文注入
项目地址：{REPO_URL}

前置分析结论（来自上一步分析）：
- 项目核心架构：{一句话描述，如"基于插件式 provider 的同步处理管线，无统一错误重试层"}
- 选定的贡献方向：{如"为外部调用补齐可配置的重试 / 退避机制"}
- 涉及的核心文件：{如 core/executor.py、client/base.py}
- 当前实现的缺陷：{直接粘贴上一步分析的"缺陷/缺失"字段}

在开始方案设计前，请重新阅读以上涉及的核心文件，确保你对当前实现有准确理解，再开始输出。

---

## 问题边界定义
请先用以下格式明确问题边界，再进入方案设计：

要解决的核心问题：（一句话）
不在本次 PR 范围内的问题：（列出 2~3 条，防止方案范围蔓延）
成功标准：（如何判断这个方案解决了问题？可量化最好）
约束条件：
- 不破坏现有公共 API 的调用方式
- 兼容项目当前支持的语言 / 运行时版本（如 Java、Python、Node 等）
- 单个 PR 的改动尽量控制在 300 行以内（必要时拆分）

---

## 方案设计（核心）
请给出 2~3 个可行的技术方案，每个方案包含：

核心思路：（2~3 句话描述设计思想）
关键设计决策：
- 新增 / 修改哪些核心抽象（class / interface / function）？
- 数据如何流动？（输入 → 处理 → 输出）
- 与现有模块的集成点在哪里？
伪代码或接口签名草稿：（只需展示关键接口，不需要完整实现）
优点：
缺点 / 风险：
适用场景：

推荐方案：方案 N

|---|---|---|

|---|---|---|
| | | |

### 实现步骤（有序）
第 1 步：{具体任务，如"在 base.py 中定义 RetryPolicy 接口"}

> 每一步都应该是一个可独立验证的小目标，完成后项目仍可运行。

### 验证策略
- 手动验证：如何跑通一个端到端的 demo 证明方案有效？
- 单元测试：至少需要覆盖哪 2~3 个核心测试用例？
- 边界情况：有哪些边界或异常情况需要特别测试？

## 与维护者沟通前的准备
在开始写代码之前，我需要在 Issue 或 Discussion 中先征求维护者意见。请帮我起草一段发给维护者的评论，内容包含：
1. 我发现的问题（客观描述，不带主观判断）
2. 我提议的解决方向（只说方案，不说全部细节）
3. 询问他们是否有兴趣接受这类 PR，以及是否有已有计划

要求：英文，语气简洁专业，不超过 150 字。
```

> 经验总结框架也可以在这一步先搭好（文章把它放在方案设计提示词的末尾）；本 skill 把完整的总结框架单独放在 §6，方便 PR 完成后再回填"成果/反馈"等需要实际结果的字段。

## 出口

产出：选定方案、问题边界、成功标准、新增/修改文件清单、有序实现步骤、给维护者的英文沟通草稿。**先把沟通草稿发出去（核心功能类必须；小改动可跳过）**，再把方案与实现规划作为前置信息带入 §4。
