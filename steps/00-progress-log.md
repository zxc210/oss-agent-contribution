# §0 进度存档与恢复（贯穿全程）

这不是四阶段里的某一步，而是贯穿 §1~§6 的一条约定。整个贡献流程跨度长——等维护者回 issue、等 PR review 都可能好几天——没有存档，换个会话就接不上了。

## 存档位置

按目标仓库分子目录归档：`_oss-work/<repo>/progress.md`（如 `_oss-work/agents-flex/progress.md`），同一仓库的 issue 正文备份等草稿也放这个子目录下。这样一个 skill 可以服务多个贡献项目，各自独立不混。整个 `_oss-work/` 在 skill 项目的 `.gitignore` 里被忽略——作战记录只在本地留痕，不进 skill 仓库，也不混入 skill 的通用方法论。

clone 下来的目标仓库另放在 skill 项目**外**的同级目录（如 `../<repo>`），彻底独立、不受 skill 的 git 影响。一个贡献流程一份档，持续更新同一个文件，不要每次新建。

## 什么时候存

- **每次要进入"等待"节点时必存**：发完沟通 issue 等维护者回应、提完 PR 等 review——这些是最容易断线的地方。
- 完成一个阶段（§1/§2/§3/§4）、拿到重要结论时顺手更新。
- 用户说"存档"时。

## progress.md 的结构模板

```markdown
# 进度存档 — 为 {仓库} 做开源贡献

> 存档时间：{日期}

## 一句话现状
走到 {§几} → {当前在等什么 / 下一步做什么}，代码{已动/未动}。

## 基本信息
| 项 | 值 |
|---|---|
| 目标仓库 | {owner/repo + URL} |
| 仓库画像 | {语言 / 协议 / star / 关键特征} |
| 本地 clone | {本地路径} |
| GitHub 账号 | {账号 + gh 登录状态} |
| 技术栈 | {贡献者技术栈} |

## 已沟通的 issue / PR
- #{号}：{链接} —— {标题}
- 状态：{等待回复 / 已回复 + 结论}

## §1~§3 的结论
{选定仓库的理由、Top3 方向、选定方案、问题边界、成功标准}

## 核实过的代码事实
{§3 读代码才拿到的事实——关键 API 签名、类的可见性约束、字段/属性约定、现有测试范式等。
这一节只在 §3 之后才有内容；它最值钱——恢复会话后照它走，不用重新摸一遍代码。}

## 事件 / 数据映射表（若方案涉及）
{如"源事件 → 目标产出"的对应关系}

## 实现规划（§4 执行依据）
{文件级新增/修改清单 + 有序实现步骤}

## 下一步（恢复会话后从这里继续）
1. {第一件事，带可直接跑的命令}
2. ...

## 相关路径速查
{本地仓库、issue 正文备份、skill 源等关键目录}
```

> "核实过的代码事实"这一节在 §3 之前为空，到 §3 读过源码后再补——它是整份档里最省时间的部分，务必写实、写全。

## 恢复流程

新会话接手时：
1. 先读 `_oss-work/<repo>/progress.md` 对齐进度（`_oss-work/` 下有多个仓库子目录时，先确认是哪个）。
2. 按"已沟通的 issue / PR"里的链接，用 `gh issue view <n> --comments` / `gh pr view <n> --comments` 查有没有新回应。
3. 从"下一步"清单的第一条继续；代码事实直接采信存档，不重复读源码。
