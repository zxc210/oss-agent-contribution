# §2 寻找贡献切入点

目标：对 §1 选定的项目，找出 1~3 个**能在 2 周内完成、且能作为一段完整工程经验系统复盘**的贡献方向。两条腿走路：现成 Issue 筛选 + 架构层缺陷分析。

> 架构缺陷分析要读源码，开始前先把目标仓库 clone 到本地（clone 位置的硬约定见 §0）。

## 用 Label 过滤适合上手的 Issue

在项目 Issues 列表里按标签过滤，优先挑这几类：

```
label:"good first issue"
label:"help wanted"
label:"bug"
label:"documentation"
label:"enhancement"
```

## 做哪些类型的贡献

按性价比与可讲性排序（结合文章作者的取舍）：

1. 修 Bug —— 从 `good first issue` 开始，门槛低、改动聚焦。
2. 新增功能 / 集成 —— 比如给项目加一个新的 provider / adapter / 格式支持，技术含量清晰、容易复盘。
3. 核心功能 —— 价值高但风险大，**务必先在 Issue 里讨论再动手，避免白做**。

> 文档/翻译、补测试用例也能被 merge、门槛更低，但技术沉淀价值相对弱；按"积累可复盘工程经验"的目标，优先选上面三类。

## 切入点分析提示词（把 {REPO_URL}、{主题} 代入后交给 AI 执行）

```
# 开源项目贡献分析

## 项目信息
GitHub 地址：{REPO_URL}
项目主题 / 领域：{主题，如 AI Agent / LLM、数据库、前端组件库、CLI 工具}
我的技术栈：{如 Java、Python、TypeScript、Go、React}
我的目标：找到 1~3 个可以在 2 周内完成、且能作为一段完整工程经验系统复盘的 PR 方向

---

## 准备工作（请先执行）
阅读以下文件以建立项目理解，文件不存在则跳过：
- README.md
- CONTRIBUTING.md
- CHANGELOG.md / HISTORY.md
- 项目主入口文件（main.py / index.ts / app.py 等）

然后输出目录结构（depth=3），标注你认为的核心模块目录，并用 2~3 句话描述：
这个项目是做什么的？核心数据流 / 主流程是怎样的？核心抽象（主要的 class / 模块 / 接口）有哪些？

---

## 分析维度一：Issue 列表筛选
访问 {REPO_URL}/issues，筛选符合以下**全部条件**的 Issue：

筛选条件：
- 标签包含 `good first issue`、`help wanted`、`bug`、`documentation`、`enhancement` 之一
- 状态为 open，近 60 天内有过活动（非 stale）
- 无人认领（无 assignee，且评论中无人声称 I'll take this / I'm working on this）
- 描述清晰，有明确的期望行为或可复现步骤
- 所需改动范围在 1~3 个文件内，不涉及整体架构重构

输出格式（表格）：
| Issue # | 标题 | 类型 | 所需技能 | 预估工作量 | 推荐理由 |

---

## 分析维度二：架构层缺陷分析
深入阅读源码，逐一检查下面的通用维度。每个维度必须定位到具体文件和函数，禁止泛泛而谈。
这些维度适用于大多数项目；请再**结合 `{主题}` 领域补充 2~4 个该领域特有的维度**（见末尾"按主题补充专属维度"），一起检查。

> **⚠️ 验证红线：别轻信"完全没有"。** 判断某能力"缺失"前，先 `grep` 全仓确认，区分三种情况：(a) 彻底没有；(b) 底层有、但某一层没接进来；(c) 有抽象/接口但没接线。给维护者的描述一旦把 (b)/(c) 说成 (a)，就是事实错误，一读代码就露馅。实测教训：某框架曾被判"完全没有可观测性埋点"，实为底层几层已默认埋点、仅上层编排未接入——准确定位应是"补齐某层"而非"从零新增"。

### 1. 错误处理与健壮性
重点检查：
- 失败路径怎么处理：是直接抛错中断，还是有重试 / 降级 / 回退机制？
- 外部依赖（网络、IO、第三方服务）超时和异常是否被妥善捕获？
- 错误信息是否清晰可定位，还是吞掉异常 / 只打印一句无上下文的日志？
- 边界输入（空值、超大输入、并发）下是否会崩溃或产生脏状态？

### 2. 可扩展性与抽象设计
重点检查：
- 核心能力是硬编码写死，还是通过接口 / 插件 / 策略模式开放扩展？
- 想新增一种实现（新的 provider / backend / 格式等）时，是否只能改源码、无扩展点？
- 抽象层次是否合理：有没有过度抽象，或该抽象处却散落着重复逻辑？
- 公共 API 的向后兼容性如何保障？

### 3. 配置与默认值
重点检查：
- 关键参数是硬编码还是可配置？默认值是否合理、是否有文档说明？
- 配置项命名 / 组织是否一致，有无散落各处、难以发现的隐藏开关？
- 是否存在"只能在初始化时设定、运行期无法调整"的不必要限制？

### 4. 可观测性（日志 / 指标 / 追踪）
重点检查：
- 关键路径有没有日志？日志级别是否得当，还是要么没有、要么刷屏？
- 是否暴露指标 / 埋点 / 事件，供外部监控或调试？若有，是否覆盖了核心路径？
- 中间状态 / 执行进度是否对调用方可见（回调、事件、流式输出等）？
- 若缺失，现有架构能否以低侵入方式补上观测点？

### 5. 性能与资源使用
重点检查：
- 有无明显的重复计算、可缓存却未缓存、N+1 式调用？
- 资源（连接、文件句柄、线程、内存）是否正确释放，有无泄漏风险？
- 热点路径是否有不必要的同步阻塞 / 锁竞争？

### 6. 测试覆盖与可测性
重点检查：
- 核心逻辑有没有测试？是只测 happy path，还是也覆盖了边界与失败路径？
- 代码结构是否便于测试（依赖可注入 / 可 mock），还是强耦合难以单测？
- 有没有明显缺测、却又容易补齐的模块，可作为低风险切入点？

### 7. 文档与 API 一致性
重点检查：
- README / API 文档 / 注释与实际代码行为是否一致，有无过时或缺失？
- 公共接口是否有清晰的用法说明和示例？
- 报错信息、参数命名是否自解释，对使用者是否友好？

### 按主题补充专属维度（`{主题}` 特有）
上面 7 条是通用骨架。**请再针对 `{主题}` 领域补充该领域真正关心的维度**，否则分析会流于表面。举例：
- **AI Agent / LLM 框架**：任务规划范式、多 Agent 协作、上下文 / token 管理、Human-in-the-loop、工具检索与路由、评估框架、Streaming。
- **数据库 / 存储引擎**：事务与隔离级别、索引与查询计划、持久化与崩溃恢复、并发控制、连接池。
- **前端组件库**：无障碍（a11y）、受控 / 非受控、主题与样式隔离、SSR 兼容、包体积与 tree-shaking。
- **CLI 工具**：参数解析与校验、退出码与管道友好、跨平台兼容、错误提示体验、自动补全。
每个补充维度同样要"定位到具体文件和函数"，并套用下面的输出格式。

### 每个维度的输出格式：
现状描述：（定位到具体文件路径 + 函数名）
缺陷 / 缺失：（当前方案存在什么问题，或完全缺失）
影响程度：high / medium / low
改进方向：（1~3 句话，描述可行的改造方案）
改动范围：（预计涉及文件数和代码行量级）
经验沉淀角度：（用一句话说明，这个贡献能锻炼或体现什么技术与工程能力）

---

## 最终输出：Top 3 贡献建议
综合以上两个维度，输出优先级排序的建议：

第 N 名：{PR 方向名称}
- 一句话描述：
- 来源维度：Issue #xxx / 代码分析-{维度名}
- 入口文件：
- 为什么适合我：（结合我的技术栈说明）
- 预计工作量：小 / 中 / 大
- 能沉淀什么：（具体说明能体现的技术决策和工程能力）
- 风险点：（可能遇到的阻力或依赖）
```

## 出口

和用户一起从 Top 3 里选定 **1 个**贡献方向，记录：方向名称、来源（Issue # 或某个分析维度）、入口文件、当前实现的缺陷。这些作为"前置分析结论"带入 §3。
