# §2 寻找贡献切入点

目标：对 §1 选定的项目，找出 1~3 个**能在 2 周内完成、且能作为一段完整工程经验系统复盘**的贡献方向。两条腿走路：现成 Issue 筛选 + 架构层缺陷分析。

> 架构缺陷分析要读源码，开始前先把目标仓库 clone 到本地（clone 位置的硬约定见 §0）。

## 用 Label 过滤适合上手的 Issue

在项目 Issues 列表里按标签过滤，优先挑这几类：

```
label:"good first issue"
label:"help wanted"
label:"bug"
label:"documentation"
```

## 做哪些类型的贡献

按性价比与可讲性排序（结合文章作者的取舍）：

1. 修 Bug —— 从 `good first issue` 开始，门槛低、改动聚焦。
2. 新增工具 / 集成 —— 比如给 Agent 框架加一个新的 tool 支持，技术含量清晰、容易复盘。
3. 核心功能 —— 价值高但风险大，**务必先在 Issue 里讨论再动手，避免白做**。

> 文档/翻译、补测试用例也能被 merge、门槛更低，但技术沉淀价值相对弱；按"积累可复盘工程经验"的目标，优先选上面三类。

## 切入点分析提示词（把 {REPO_URL} 代入后交给 AI 执行）

```
# 开源项目贡献分析

## 项目信息
GitHub 地址：{REPO_URL}
我的技术栈：{如 Python、TypeScript、React、MCP 集成、LangChain.js}
我的目标：找到 1~3 个可以在 2 周内完成、且能作为一段完整工程经验系统复盘的 PR 方向

---

## 准备工作（请先执行）
阅读以下文件以建立项目理解，文件不存在则跳过：
- README.md
- CONTRIBUTING.md
- CHANGELOG.md / HISTORY.md
- 项目主入口文件（main.py / index.ts / app.py 等）

然后输出目录结构（depth=3），标注你认为的核心模块目录，并用 2~3 句话描述：
这个项目的核心 Agent 循环是什么？使用了哪种规划范式？

---

## 分析维度一：Issue 列表筛选
访问 {REPO_URL}/issues，筛选符合以下**全部条件**的 Issue：

筛选条件：
- 标签包含 `good first issue`、`help wanted`、`bug`、`enhancement` 之一
- 状态为 open，近 60 天内有过活动（非 stale）
- 无人认领（无 assignee，且评论中无人声称 I'll take this / I'm working on this）
- 描述清晰，有明确的期望行为或可复现步骤
- 所需改动范围在 1~3 个文件内，不涉及整体架构重构

输出格式（表格）：
| Issue # | 标题 | 类型 | 所需技能 | 预估工作量 | 推荐理由 |

---

## 分析维度二：架构层缺陷分析
深入阅读源码，逐一检查以下 7 个维度。
每个维度必须定位到具体文件和函数，禁止泛泛而谈。

> **⚠️ 验证红线：别轻信"完全没有"。** 判断某能力"缺失"前，先 `grep` 全仓确认，区分三种情况：(a) 彻底没有；(b) 底层有、但某一层没接进来；(c) 有抽象/接口但没接线。给维护者的描述一旦把 (b)/(c) 说成 (a)，就是事实错误，一读代码就露馅。实测教训：agents-flex 曾被判"框架无任何 OTel"，实为底层三层（HTTP/chat/tool）已默认埋点、仅 Agent 编排层未接入——准确定位应是"补齐某层"而非"从零新增"。

### 1. 任务规划（Task Planning）
分析项目当前使用的规划范式（ReAct / Plan-and-Execute / CoT / 无显式规划）。
重点检查：
- 任务能否被分解为子任务？有无显式的 Plan 生成步骤？
- 子任务执行失败时，是否有动态重规划机制，还是直接报错退出？
- 规划结果是否可被持久化，以支持断点续跑？
- 若项目完全没有规划层，直接依赖 LLM 单步决策，是否存在引入规划层的空间？

### 2. 多 Agent 协作
分析项目的 Agent 拓扑结构。
重点检查：
- 当前是单 Agent 还是多 Agent 架构？
- 若是单 Agent：是否存在天然适合拆分为 Orchestrator + Worker 结构的场景？
- 若已是多 Agent：通信协议是什么？角色职责是否清晰？结果聚合策略是否合理？
- Agent 之间是否存在状态共享机制，还是完全无状态地串行调用？

### 3. 上下文管理策略（Context Management）
分析项目如何处理长对话和 token 限制问题。
重点检查：
- 当 context 接近模型 token 上限时，策略是什么（硬截断 / 滚动窗口 / 摘要压缩）？
- 压缩或截断策略是否会丢失关键的工具调用历史或中间结果？
- 跨轮次的对话历史如何存储和读取？是否存在冗余或浪费？
- 是否有针对不同类型信息（系统指令 / 工具结果 / 对话历史）的差异化管理策略？

### 4. Human-in-the-loop 机制
分析 Agent 在执行过程中是否支持人工干预。
重点检查：
- 遇到低置信度决策或高风险操作（文件写入、外部 API 调用、消息发送等）时，是否有暂停并等待人工确认的机制？
- 是否有 Checkpoint 机制，支持 Agent 执行中断后从断点恢复？
- 人工介入后，Agent 能否将人的反馈融入后续决策，还是只能重头开始？

### 5. Agent 评估框架（Evaluation）
分析项目是否具备系统评估 Agent 表现的能力。
重点检查：
- 是否有 eval 模块或测试集？评估粒度是只看最终结果，还是追踪完整 trajectory？
- 是否集成了外部评估工具（LangSmith / Arize / 自定义 pipeline）？
- 工具调用的选择是否正确、参数是否合理，有没有被量化追踪？
- 若完全没有评估机制，引入最小可用 eval pipeline 的改造成本是多少？

### 6. Tool 检索与路由（Tool Retrieval）
分析项目的工具管理和选择机制。
重点检查：
- 当前是全量工具注入（所有 tool schema 塞入 system prompt）还是按需检索？
- 若工具数量超过 20 个，是否有向量化检索机制按任务动态选取相关子集？
- 工具的描述质量如何？是否存在语义相似导致 LLM 选择混乱的问题？
- 是否支持 MCP 协议？若不支持，现有 tool 层是否有接入 MCP 的改造空间？

### 7. Streaming 与中间状态可见性
分析 Agent 执行过程的实时可见性。
重点检查：
- 是否支持流式输出（streaming token by token）？
- Agent 的中间状态（当前在执行哪个子任务、调用了什么工具、参数是什么）是否对外暴露？
- 是否有事件/状态订阅接口，供前端实时展示 Agent 执行进度？
- 若缺失，现有架构是否支持以低侵入性方式引入 streaming 和状态广播？

### 每个维度的输出格式：
现状描述：（定位到具体文件路径 + 函数名）
缺陷 / 缺失：（当前方案存在什么问题，或完全缺失）
影响程度：high / medium / low
改进方向：（1~3 句话，描述可行的改造方案）
改动范围：（预计涉及文件数和代码行量级）
经验沉淀角度：（用一句话说明，这个贡献能锻炼或体现什么技术与工程能力）

---

## 最终输出：Top 3 贡献建议
综合以上两个维度，输出优先级排序的建议：

第 N 名：{PR 方向名称}
- 一句话描述：
- 来源维度：Issue #xxx / 代码分析-维度X
- 入口文件：
- 为什么适合我：（结合我的技术栈说明）
- 预计工作量：小 / 中 / 大
- 能沉淀什么：（具体说明能体现的技术决策和工程能力）
- 风险点：（可能遇到的阻力或依赖）
```

## 出口

和用户一起从 Top 3 里选定 **1 个**贡献方向，记录：方向名称、来源（Issue # 或维度 X）、入口文件、当前实现的缺陷。这些作为"前置分析结论"带入 §3。
