# §4 代码实现

目标：按 §3 的推荐方案与实现规划，在本地仓库里逐步写代码并验证，产出可提交的改动 + 测试 + commit 计划。**先读后写，逐步可验证。**

## 代码实现提示词（把前置信息代入后交给 AI 执行）

```
# 技术方案实现

- 需要新增的文件：{文件路径 + 职责}

- 实现步骤：{有序步骤列表}

## 实现前的准备
在写任何代码之前，请先执行以下操作：
1. 阅读所有需要修改的文件，理解当前实现
2. 检查项目的代码风格规范：
   - 有无 .eslintrc / pyproject.toml / ruff.toml 等配置文件？
   - 现有代码使用的命名风格（snake_case / camelCase）？
   - 注释和 docstring 的书写习惯？
   - 类型标注的完整程度？
3. 确认当前主分支可以正常运行（跑通 README 中的 quickstart 或现有测试）

确认以上三点后，再开始实现，禁止边读边写。

---

## 实现原则
最小侵入性：
- 优先扩展，而不是修改现有函数
- 若必须修改现有函数，只改必须改的部分
- 新增的公共接口保持向后兼容

逐步实现，每步可验证：
严格按照方案中的实现步骤顺序执行，每完成一步，项目必须仍处于可运行状态，不允许出现中间状态的残缺代码。

风格一致性：
新代码的命名、注释、类型标注风格必须与现有代码保持一致，不要引入项目中没有使用的新依赖，除非确实必要。

---

## 实现流程

### Step 1：接口定义（先定义，后实现）
首先只定义新增的核心接口、类签名、函数签名，不写具体实现（函数体用 pass 或 raise NotImplementedError）。
完成后停下来，输出：
- 新增了哪些文件 / 接口
- 这些接口如何与现有代码衔接
- 有无发现方案设计时遗漏的依赖或冲突
确认接口设计合理后，再进入下一步。

### Step 2：核心逻辑实现
按照实现步骤依次完成每个文件的具体逻辑。
每个文件完成后输出：
- 文件路径
- 实现了什么
- 与方案设计有无偏差，若有，说明原因

### Step 3：集成到现有代码
将新模块接入现有的调用链。
重点检查：
- 原有的调用方式是否仍然有效（不破坏现有用法）
- 新功能的触发路径是否完整
- 有无遗漏的错误处理分支

### Step 4：验证
按照方案中的验证策略逐项执行：
手动验证：给出一个最小可运行的 demo 脚本，直接在终端可以跑通，证明核心功能有效。
单元测试：为以下场景各写一个测试用例：
- 正常路径（happy path）
- 边界情况（如空输入、超长输入、工具调用失败）
- 与现有功能的兼容性（原有用法不受影响）
测试文件放在项目现有的测试目录下，命名风格与现有测试文件一致。

## 实现过程中的注意事项
遇到以下情况时，停下来告诉我，不要自行决定：
- 发现方案设计有遗漏，需要改动超出预定范围的文件
- 发现与现有代码存在冲突，无法在不破坏兼容性的前提下实现
- 有两种实现方式，各有利弊，需要人工决策
- 需要引入新的第三方依赖

遇到以下情况时，自行处理，但实现后说明：
- 方案中的伪代码需要调整以适配实际代码结构
- 需要补充方案中未提及的错误处理逻辑
- 测试用例的具体写法与方案描述略有不同
```

## 出口

产出：改动代码 + 测试 + 改动摘要表 + 2~4 个 commit 的拆分计划。确认本地测试跑通、项目仍可运行后，进入 §5 提 PR。
