# §6 跟进与经验总结沉淀

目标：PR 提交后持续跟进，并把整段经历沉淀成一份结构化的开源贡献经验总结。

## 提交 PR 后要做什么

- **时常关注维护者有没有提出 review 意见**，有反馈及时响应、按建议迭代。
- **超过约 1~2 周没有回应**（对齐 §1 健康度里"PR 一般 < 2 周有回应"的口径），可以给维护者发邮件/在 PR 里礼貌地 ping 一下进度。

## 经验总结框架

把这段经历按下面六段沉淀下来，作为一次完整的贡献复盘：

### 背景（Context）
这个项目是什么？在它所属的领域里解决什么问题？我为什么选择给它做贡献？发现了什么架构层面的缺失？

### 我做了什么（Contribution）
一句话说清楚我的贡献：我为这个项目实现了 / 改进了 / 引入了什么？这个改动在项目中处于什么位置？影响哪些使用路径？

### 我怎么分步做的（Process）
按实际实现顺序，列出 3~5 个关键步骤。每步聚焦在"我做了什么决定"，而不是"我写了什么代码"。例：
- 第一步：分析现有架构，确定改动的最小侵入点
- 第二步：设计接口，对比了 A 方案和 B 方案，选择 B 因为……
- 第三步：……

### 成果（Result）
- PR 状态：（已合并 / 审核中，附链接）
- 对项目的影响：（功能层面带来了什么变化）
- 可量化的指标：（如有，如 token 减少 X%、响应时间降低等）
- 维护者的反馈：（直接引用 review 评论中的关键句）

### 遇到的困难（Challenges）
列出 1~2 个真实的技术卡点，格式：
- 困难描述：我遇到了什么问题？
- 我的解决过程：我怎么排查和解决的？
- 结论：最终怎么处理的？
> 这部分最有沉淀价值，要具体，不要说"遇到了一些问题"。

### 下次可以怎么优化（Reflection）
如果重新做一次，我会在哪些地方做得不同？
- 技术层面：有没有更优雅的实现方式？
- 流程层面：沟通维护者的时机、PR 拆分方式是否合理？
- 范围层面：是否做了不必要的改动，或者遗漏了重要边界情况？

### 沉淀下来的核心能力
列出 2~3 条，这次贡献真正锻炼或体现了哪些技术与工程能力。

## 出口

整段流程闭环：从找项目到 PR 到经验沉淀。PR 合并后回填"成果"段的链接、指标与维护者反馈，这段经历即成为一份完整的开源贡献经验记录。
